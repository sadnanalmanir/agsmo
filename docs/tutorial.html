Mental model

One picture for all lessons. A plan is a root Goal with ordered SubGoals — there is no separate Plan class. Each lesson below has a Mermaid instance diagram (easy to edit as text).

Agent ──performedBy──► Action ──hasOutcome──► Outcome ▲ │ achievedBy Episode ◄──partOf── Goal/SubGoal ──hasConstraint──► Constraint │ └──hasSubGoal──► SubGoal (stepIndex 0..n)
  • status on goals: active · completed · failed · abandoned
  • stepIndex orders plan steps (0-based); next open step = lowest active index
  • rationale on actions answers “why did you do X?”
  • Actions/Outcomes are also typed as prov:Activity / prov:Entity

03 Action, outcome, explain

Execute one step: Action + Outcome + rationale for explainability. PROV dual-typing included.

01 minimal02 plan03 action04 full05 failure

Story

The agent implements plan APIs offline-first, records why, and marks the step completed via a successful outcome.

Key triples

agsmo:goal-write-api agsmo:achievedBy agsmo:action-implement-api .

agsmo:action-implement-api a agsmo:Action , prov:Activity ;
  agsmo:rationale "Plan APIs must live…" ;
  agsmo:hasOutcome agsmo:outcome-api-green ;
  prov:wasAssociatedWith agsmo:agent-alice .

agsmo:outcome-api-green a agsmo:Outcome , prov:Entity ;
  agsmo:success true ;
  prov:wasGeneratedBy agsmo:action-implement-api .
You should observe Non-empty rationale; outcome success true; goal linked with achievedBy. This is how “Why did you do X?” is answered from the graph.

Anti-patterns Common mistakes (bad vs good)

Correct AGSMO is easier to learn when you also see what not to do. Each pair below is a small Turtle graph. Most bad graphs fail first-cut SHACL; all good graphs pass. Full files live under examples/anti-patterns/.

01 · Bad — no stepIndex

agsmo:step-a a agsmo:SubGoal ;
  agsmo:description "Design API" ;
  agsmo:status "active" .
  # missing stepIndex

Order of plan steps is undefined; “next open step” is unreliable.

01 · Good — ordered steps

agsmo:step-a a agsmo:SubGoal ;
  agsmo:description "Design API" ;
  agsmo:status "active" ;
  agsmo:stepIndex 0 .

Stable order for multi-step plans.

02 · Bad — orphan action

agsmo:act-search a agsmo:Action ;
  agsmo:description "Queried the index" ;
  agsmo:performedBy agsmo:agent-x .
# no Goal --achievedBy--> Action

Cannot answer “in service of which goal?” (modelling issue; first-cut SHACL may still pass).

02 · Good — linked action

agsmo:goal-search
  agsmo:achievedBy agsmo:act-search .
agsmo:act-search
  agsmo:hasOutcome agsmo:out-search .

Planning + explainability stay connected.

03 · Bad — no performer

agsmo:act-x a agsmo:Action ;
  agsmo:description "Did the work" .
  # missing performedBy

Fails SHACL ActionShape; no accountable agent.

03 · Good — performedBy

agsmo:act-x a agsmo:Action ;
  agsmo:description "Did the work" ;
  agsmo:performedBy agsmo:agent-x .

04 · Bad — free-text status

agsmo:goal-x agsmo:status "done" .

Not in controlled set; tools looking for completed miss it; SHACL fails.

04 · Good — controlled status

agsmo:goal-x agsmo:status "completed" .

Use: active · completed · failed · abandoned.

05 · Bad — outcome without success

agsmo:out-x a agsmo:Outcome ;
  agsmo:description
    "Suite finished with issues" .
  # missing success true/false

Cannot filter successes vs failures; SHACL fails.

05 · Good — boolean success

agsmo:out-x a agsmo:Outcome ;
  agsmo:description
    "Suite finished with issues" ;
  agsmo:success false .
CI tests/test_anti_patterns.py ensures bad structural cases fail SHACL and good pairs pass. Files: examples/anti-patterns/

Try it (Python)

Always parse the ontology first, then an example file.

from rdflib import Graph

g = Graph()
g.parse("ontology/agsmo.ttl", format="turtle")
g.parse("examples/04_literature_review_full.ttl", format="turtle")

q = """
PREFIX agsmo: <https://w3id.org/agsmo/ns#>
SELECT ?step ?desc WHERE {
  ?sg a agsmo:SubGoal ;
      agsmo:status "active" ;
      agsmo:stepIndex ?step ;
      agsmo:description ?desc .
}
ORDER BY ?step
LIMIT 1
"""
for row in g.query(q):
    print(int(row.step), row.desc)
# Expected: 1 Summarize key architectures and trade-offs
